## 1. The promise I tested

> Someone arms a fault on a real file, writes the file anyway, and does not record a land.
> `serve` puts the file back by itself once the TTL expires, and `status` / `/health` / `/metrics`
> tell you what happened.

That is the whole product in one loop, and it is the loop a stranger would run first: arm, break,
watch, read the report. I ran it end to end from a scratch build (`go build ./cmd/mischief`) on a
sandbox host, with an explicit sanction file, against a throwaway runs dir.

## 2. What actually happened (transcript, paraphrased to the load-bearing lines)

```
$ mischief arm --fault S-001 --target scratch:$W --ttl 6s \
    --inverse-kind restore-file --inverse-params path=$W/config.toml,backup=$W/config.toml.bak \
    --check-kind file-matches-backup --check-params path=$W/config.toml,backup=$W/config.toml.bak \
    --dir $RUN
armed S-001 ... hold ... ttl 6s                      -> rc=0
$ printf 'FAULTED' > $W/config.toml                  # break it, do not land
$ mischief serve --dir $RUN                          # sweeper running
$ mischief status --dir $RUN --json
  -> hold armed, ttl_remaining -3s (still armed, past its TTL, file still FAULTED)
$ ... at +10.0s the file is back to "original"       # revert happened, late
$ mischief health --dir $RUN --json | grep outcome
  -> "not_landed"
```

The protection loop works: nothing needed my hands, the file came back byte-identical to the backup,
and the run is reported honestly afterwards. That is the value, and it is real.

What is not real is the arithmetic users are sold.

### 2a. The documented retention command does not run — row **DOC-27** (P2)

`docs/OPERATIONS.md:138` tells an operator, in the backup-before-you-delete step:

```
mischief retention --dir <run dir>     # report old run dirs; --apply rotates them
```

```
$ mischief retention --dir $RUN
flag provided but not defined: -dir
usage: mischief retention [-runs-dir DIR] [-apply] ...        rc=2
$ mischief retention -runs-dir $RUN
DRY-RUN PLAN (nothing executed)
retention: 0 action(s)                                         rc=0
```

The doc's own example is the one command the binary rejects. This is the step someone runs
immediately before deleting a journal directory — the worst place for a copy-paste to fail with
a usage dump, because the failure looks like "nothing to retain" rather than "your command was
wrong", and the operator proceeds to delete by hand.

### 2b. The TTL is quantized, and no user-facing doc says so — row **MISCHIEF-DF-59-R2** (P3, recurrence)

Measured on HEAD at 100 ms resolution (poll the target until restored):

| declared TTL | reverted at | late by | overshoot |
|---|---|---|---|
| 4 s | 8.511 s | +4.511 s | 113 % |
| 6 s | 10.039 s | +4.039 s | 67 % |
| 10 s | 14.903 s | +4.903 s | 49 % |

Every case is late, none is early, and the lateness is bounded by one 5 s heartbeat. So the code
does exactly what the internal comment says (`internal/reverter/doc.go:68`, quantized to the sweep)
— the defect is that `README.md` and `docs/OPERATIONS.md` describe the TTL as if it were a timer.
An operator who sizes a TTL at 4 s to bound a blast radius gets 8.5 s of exposure and no warning.
`mischief status` also keeps reporting the hold as armed with a **negative** `ttl_remaining`
during that window, which reads as "about to revert" when it means "already overdue".

This is the recurrence of MISCHIEF-DF-59, whose FIXUP half already repaired the second-truncation
and added the quantum comment; the user-facing half is still open, so I cited that row instead of
filing a bare sibling.

### 2c. The "closed vocabulary" in the docs is not closed — row **DOC-28** (P3)

Same scrape, after three late reverts, all three of which restored the file:

```
mischiefd_revert_total{result="no_hold"} 0
mischiefd_revert_total{result="not_landed"} 3
mischiefd_revert_total{result="revert_failed"} 0
mischiefd_revert_total{result="reverted"} 0
```

`docs/OPERATIONS.md:54` does list `not_landed` (health table), but the metrics table at `:81`
enumerates only `reverted`, `revert_failed`, `no_hold`. Anyone building a dashboard from the
documented list silently undercounts every revert that this loop produces by default; anyone
alerting on `reverted` alone sees zero while the product is working.

A related oddity, recorded on the row rather than fixed here: a successful restore is counted
`not_landed`, never `reverted`, so the label an operator would naturally alert on (`reverted`)
is unreachable in the documented loop.
